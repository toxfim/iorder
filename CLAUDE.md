# iOrder.uz

Internal B2B ordering and order-tracking platform for ONE trading company in Uzbekistan.
NOT multi-tenant SaaS. NOT a marketplace. Third-party sellers cannot list goods.

Goals (priority order): 1) visibility of order status, 2) stop manual Excel price list distribution via Telegram.

## Stack (ADR-001, status: Accepted 2026-10-19; hosted on the owner's shared server since 2026-11-06, staging and production side by side)

- Modular monolith: `apps/api` (backend + worker), `apps/staff` (staff Vue app), `apps/customer` (customer Vue app), `packages/shared`, `packages/web-core` (frontend kit shared by the two web apps)
- TypeScript, Node.js, NestJS, PostgreSQL, Prisma, pg-boss (jobs)
- Validation: zod (the only validation library)
- Vue 3 + Vite + vue-i18n; two apps [C, 2026-10-25]: `apps/customer` and `apps/staff`, each used as Telegram Mini App and website, with shared frontend code in `packages/web-core` (ADR-001 §3.5)
- Telegram bot: grammY (webhook in production, long polling in dev/test). Google Sheets: read-only service account

## Hard rules (never break)

1. Money is fixed-point decimal, never float. Currency shown to customers: UZS.
2. `orders.status` changes ONLY through one transition function: conditional update on expected status + `order_events` row + `notification_outbox` rows, all in ONE DB transaction. Illegal transitions are rejected on the server.
3. `order_events` is append-only (no update/delete).
4. Orders store a price snapshot (`order_items`). Later price list changes never alter existing orders.
5. Exactly one `PUBLISHED` price list version; published versions are immutable.
6. Customer isolation: a customer sees only their own organization's orders, prices, discounts. Enforce in queries (server), never only in the UI. Needs an automated test.
7. Cost data (purchase price, rate, margin, supplier) is staff-only. Customer API returns allow-listed fields only. Needs an automated test.
8. Validate every untrusted input at the boundary. Verify Telegram signatures (init data / ID token) before trusting anything from Telegram.
9. Business time rules (scheduled posts, displayed accounting hours) use Asia/Tashkent. Store timestamps in UTC.
10. The app never writes to the Google Sheet «Поставка»: the sheet is the only source of real stock. iOrder never subtracts permanently; it only holds stock (`order_allocations`) from manager approval until `RELEASED`, `REJECTED` or `CANCELLED`. Available = per live line, sheet available minus that line's active holds (never below zero), added up per product and computed on read [C, 2026-10-30].
11. Payment status (`UNPAID`/`PAID`) is separate from fulfillment status and never blocks ordering.
12. Full history: every action is recorded in the same transaction as the change (who, when, what changed from what to what, what was sent). Order actions go to `order_events`, other actions to `audit_log`, notifications stay in `notification_outbox`. History is never updated or deleted.

## Confirmed rules to remember

- Manager approval is always required (every day, including Sat/Sun).
- Accounting approval is normal for every order, on any day. The MANAGER may tick "skip accounting" when approving; the order then continues without accounting approval but the accountant still sees it as new. There is no weekend/calendar rule (changed 2026-10-20).
- Cost (purchase price in USD, read from the Google Sheet) and the USD rate are stored in the database, staff-only, and never shown to customers (one owner exception [C, 2026-10-28]: the USD rate is printed in the price list Excel file and its group post caption). Selling prices are separate values in the price list. How the selling price derives from cost is still open.
- Only the MANAGER cancels an order [C, 2026-10-22, owner: customers and shop owners can never cancel]. Customers (shop owner and sellers), admin, accountant, warehouse and driver cannot. A cancellation always needs a reason; the person who placed the order is notified with the reason as written. Rejections (manager at `SUBMITTED`, accountant at `MANAGER_APPROVED`) are different transitions and are unchanged.
- Admin is a management role only: it does not perform workflow steps (approvals, item edits, release, delivery, receipt, accounting skip, cancellation). It configures and corrects or voids a wrong organization payment.
- Staff (including the company's accountants and managers who sit in customer Telegram groups) are never organization members; their Telegram IDs are ignored when reading group membership. This stays true when a staff member opens the customer app: they are a staff viewer there, not a member (next bullets).
- Warehouse flow [C, 2026-10-30]: after manager approval the warehouse sees the order and prepares and scans it, but cannot release until accounting cleared it or the manager skipped accounting; scanning stays mandatory for release. It also sees orders approved and later cancelled. [P]: the same for an accountant's rejection, codes voided on reject and cancel, a "Returned" action (`GOODS_RETURNED` event + `goods_returned_at/by`) (lifecycle 3.4).
- Manager may edit items/quantities only while `SUBMITTED`. Customer does not re-confirm.
- "Released by warehouse" and "driver picked up" are one step (`RELEASED`). No `IN_DELIVERY`.
- Seller sees all orders of their organization; owner approval is not required.
- Organization = Telegram group. One person = one organization for now.
- No quantity tiers, no online payment, no Corex integration in MVP.
- Payment method [C, 2026-10-24]: the manager MUST choose `CASH` ("Naqd") or `OFFICIAL` per order when approving and may change it later (not on rejected/cancelled orders). Only manager, accountant and purchasing manager see it. Separate from payment status; never blocks the workflow (lifecycle 4.1).
- Payment plan ("To'lov turi") [C, 2026-10-29, changed 2026-10-30]: `FULL` (bittada to'lash, sale price) or `DEFERRED` (bo'lib to'lash, deferred price). The customer chooses in the cart, which shows both totals and warns that the choice changes the price; the catalog shows the sale price only. Nothing is preselected: the cart has no plan until the customer picks one, and a choice is never carried into the next order. The choice is two radio cards with a visible circle and a title that says a choice is required [C, 2026-11-09]; until a plan is chosen the summary button reads "To'lov turini tanlang", is NOT natively disabled, and pressing it only takes the customer to the choice (scroll, focus, a ring that stays until a plan is picked). Real disabling is kept for the blocked cases, and the staff viewer state wins over "choose a plan". A cart with a product without a deferred price cannot choose `DEFERRED` (the server refuses it too, never guesses a price). After submitting the customer may change ONLY the plan, within a window (default 3 minutes from `submitted_at`, env `PAYMENT_PLAN_CHANGE_WINDOW_SECONDS`) and only while `SUBMITTED`; the server decides with the application Clock. The manager may change the plan while `SUBMITTED`, without a window. Both recompute from the order's own snapshot of both prices, which is immutable. Visible to the customer and the staff who see money, never to warehouse or driver. NOT the payment method `CASH`/`OFFICIAL`, whose label "Savdo turi" is confirmed [C, 2026-10-30], and never to be merged with it (lifecycle 3.3).
- Customer sign-in [C, 2026-10-24]: inside the Telegram Mini App the customer is signed in automatically (verified init data + group membership), no login. In a normal browser: "Continue with Telegram" or login/password. Customers create their own login/password only from a Telegram-authenticated session; no public self-registration (`docs/architecture/customer-website-auth.md`). Customer logins and staff logins are separate namespaces [C, 2026-10-28]: a login is unique within its scope, the staff password endpoint looks only among staff logins, and a customer never learns whether a staff login exists ("already taken" is per scope). Changed [C, 2026-11-09]: the CUSTOMER password endpoint also accepts a staff login (customer login tried first, staff login second [P]) and then opens a staff VIEWER session; the customer credential endpoints stay customer-only.
- Staff in the customer app [C, 2026-11-09]: staff members may open the customer app (website and Mini App) with their staff login and password, "Continue with Telegram" or Mini App init data. There they are a "staff viewer": no staff role applies on customer routes, no organization membership. They see the catalog and the published prices through the customer DTOs (never cost, rate, margin or supplier) and have a personal cart that belongs to no organization; orders, the amount to pay and received goods are empty; they never see a real organization's orders, debt, discounts or members. A viewer session opened on the customer site never works on a `/staff` route. Placing an order is refused by the server (`STAFF_ORDERING_DISABLED`) unless the api setting `STAFF_ORDERING_ORGANIZATION_ID` names an ACTIVE organization: STAGING ONLY, the order is then an ordinary order of that one test organization placed by the staff member; production leaves it empty. [P]: only staff roles that may browse the price list are viewers (manager, accountant, admin, purchasing manager; not warehouse or driver, who never see a price); a viewer reads only the test orders they placed themselves. Details: `docs/architecture/customer-website-auth.md`.
- Session lifetime [C, 2026-11-09]: a website session (staff site and customer site, one table) lasts 14 days without use and 90 days in all [P]; whoever opens the site once in two weeks is not asked to sign in again, also after closing the browser. The web apps keep the token in `localStorage` (`@core/lib/session-token-store`; it was `sessionStorage`, which a closed tab throws away), never in a URL or a cookie. Every way a session ends early is unchanged.
- Staff continue on the customer site [C, 2026-11-09]: the dashboard hands a signed-in staff member over with a one-time code (`POST /staff/customer-site/handoff`, action `OPEN_CUSTOMER_SITE`: the viewer roles; 256 bits, stored hashed, 60 seconds [P], single use, bound to the dashboard session) in the URL fragment; the customer site exchanges it (`POST /customer/auth/handoff`) for a VIEWER session, never a staff one. The viewer session records its source (`staff_sessions.source_session_id`) and ends with it: a dashboard sign-out revokes it, a lapsed dashboard session refuses it. Opening the customer site directly continues too: a non-secret hint cookie on the shared parent domain sends the browser to the dashboard's `/handoff` page once per browser and hour (never within twelve hours of an explicit sign-out there); `/handoff` acts only on the person's intent (the card press, or the customer site as referrer), otherwise it shows a button. Both addresses come from the api (`WEB_APP_URL`, `STAFF_WEB_APP_URL`), never from a request: no open redirect, and no new variable (`docs/architecture/customer-website-auth.md`).
- Own profile [C, 2026-11-09]: every person changes their OWN full name and phone from their profile, as often as needed: a customer with `PUT /me/contact` (the first-order dialog's route; the old "once" rule and `CONTACT_ALREADY_SET` are gone, `needsContact` still drives the first order), a staff member with `GET/PUT /staff/me/profile` in the staff app (a staff viewer's profile in the customer app is read-only). No route takes a user id; only name and phone can change; throttled; audited with before/after (`docs/domain/data-model.md`, "Own profile").
- Customer order states [C, 2026-11-09]: everywhere in the customer app an order shows one of three states, in words, never by colour alone: "Qabul qilindi" (`SUBMITTED`, `MANAGER_APPROVED`, `ACCOUNTING_CLEARED`, `RELEASED`), "Yetkazib berildi" (`DELIVERED`, `RECEIVED`), "Rad etildi" (`REJECTED`, `CANCELLED`, with the reason). Display only: the api sends the real status and behaviour (the "Qabul qildim" button at `DELIVERED`, the cancel hint, the payment badge) keeps using it. No progress bar. The order history lists only: accepted, changes to the order (lines, payment plan), delivered, refused with the reason; never the steps inside the company. The list's status filter has the three states. One mapping module: `apps/customer/src/features/customer-orders/domain/order-display.ts` (lifecycle 2.1).
- Staff bot notifications [C, 2026-10-25]: every staff member except an administrator gets a private bot message for each order update of their role, with two buttons to that order: "Open on the website" and "Open in the Mini App". A staff member without a Telegram id or without a started bot sees a reminder in the staff app; its one-time `t.me/<bot>?start=` link connects the bot and stores their Telegram id (lifecycle 6.1). Since 2026-10-28 [C] a staff account is created WITH its Telegram id (mandatory in `POST /staff/users`): the bot recognises staff in customer groups only by the id, and an unlinked staff member would be recorded as a customer member. Accounts created before that date may still be unlinked. The id can be replaced but never removed [C, 2026-10-28].
- Staff Mini App [C, 2026-11-09]: staff use the staff app as a Telegram Mini App too and are signed in automatically by their linked Telegram id (no form); a launch that cannot be signed in as staff gets a screen that says what to do. The "Open in the Mini App" button opens the staff Mini App's direct link (`TELEGRAM_STAFF_MINI_APP_URL`, `?startapp=order_<id>`) once the owner registers it in BotFather. An optional separate staff bot (`STAFF_MINI_APP_BOT_TOKEN`, off by default) makes it the only bot whose init data gives staff power. Details and owner steps: `docs/architecture/customer-website-auth.md`, "The staff Mini App". Staff bot `/start` [C, 2026-11-10]: `@iorder_staff_bot` (prod) answers a staff member with "Xayrli tong, <name>!" and one row: "Brauzerda ochish" (no colour) + "Ilovada ochish" (blue `web_app`); others get "for staff only" (`STAFF_BOT_WEBHOOK_SECRET`, same doc).
- Customer bot messages [C, 2026-11-09]: the customer side (the organization's Telegram group) gets a bot message about an order ONLY when the manager approves it, when it is rejected (manager or accountant) or cancelled (the placer also gets the cancellation reason in private), and when the manager changes its lines or its payment plan. Accounting clearance, release, delivery, receipt, payments and the customer's own actions send nothing to the customer side; events, the timeline and staff messages are unchanged. One table decides it: `CUSTOMER_SIDE_NOTIFICATIONS` in `modules/orders/customer-notification-rules.ts`. Each such message has two buttons instead of a link ("Open in the app" = the Mini App direct link `?startapp=order_<id>`, "Open in the browser"; both `url` buttons in a group) and, in the group, mentions the person who placed the order by Telegram id (a `text_mention` entity, plain text otherwise; usernames are not stored). This replaces the earlier idea of "three customer states" for bot messages (lifecycle 6.3).
- Organization debt [C, 2026-10-26; USD rule C, 2026-10-29/30]: the debt is per organization, in USD: the USD totals of its `RECEIVED` orders minus the USD values of its live payments. Each order keeps the USD rate from when it was placed; an edit or a plan change recomputes its USD total with that stored rate, never the current one. Only the manager records a payment, for the organization, never for an order (amount, currency USD or so'm chosen per payment, a required rate on a so'm payment, day that may be in the past, optional comment); only the admin corrects or voids one. An order's `PAID`/`UNPAID` is derived in USD (oldest received order first), never set by hand. Overpayment is kept; its handling is open. The customer sees only the amount to pay, in so'm at the current rate [P]. Rounding [P, not owner-confirmed]: USD is kept at 6 decimals (half up), a USD-priced line is quantity x its USD price snapshot, a so'm-priced line is so'm / frozen rate, and a difference under half a cent ($0.005, `USD_SETTLED_UNDER`) is settled; displays stay at 2 decimals (lifecycle 4).
- Purchasing manager [C, 2026-10-30]: role `PURCHASING_MANAGER`, created like any staff account with a Telegram id. Sees every page the sales manager sees, read-only, including cost, Savdo turi and customer payments, and may press the sheet sync; changes nothing else. Bot messages only for orders holding a marked product (`products.marking_required`, data set by the manager): new order, an edit adding a marked product, cancellation (lifecycle 5, 6.1.1).
- Price list editing [C, 2026-10-28, page rebuilt from design v8 the same day]: the staff app has NO drafts and NO edit mode. A row of Narxlar opens "Narxni o'zgartirish" (one product); its save (or "Price listdan olib tashlash") publishes a new PUBLISHED version at once (`POST /staff/price-list/publish`, one upsert or one removal, `baseVersionNumber` for optimistic concurrency). "Ostatokdan qo'shish" opens Ostatok filtered to stock products without a price (`?priced=unpriced`); "Narx qo'yish" there opens the same dialog. Products with zero or unknown stock may be priced; a price below the latest cost is only warned about, never blocked. The api's draft endpoints remain (unused by the app) until the owner decides to remove them.
- Price list Excel post [C, 2026-10-28]: the same .xlsx (layout of `docs/template.xlsx`) goes to every organization group, caption "Sana" + "Kurs", one `url` button to the customer prices page (for now `WEB_APP_URL/prices`; `web_app` buttons are rejected in groups). The staff prices page downloads the same file.
- Stock holds [C, 2026-10-30]: approval carries a plan of delivery lines (default FIFO, the manager may choose others). A customer's submit never waits for a hold and reserves nothing; since 2026-11-09 it is refused only above the free stock shown to them (next bullet). After approval nothing changes by itself: a line below its holds only shows a flag and a ready FIFO alternative, since this order's own shipment may be why. Delivery lines are read under the `price_reference_sync` lock, always BEFORE the order row (lifecycle 3.5).
- Order details [C, 2026-10-30]: the accountant sees supply id, product id, name, price, line total, party, and how many pieces of a line sit on each supply; `CASH` shows a warning that there is no invoice ("счёт-фактура") and the accountant still approves; Savdo turi (`paymentMethod`) and To'lov turi (`paymentPlan`) stay two names. The warehouse sees supply, party, product, quantity, no money. The accountant's approval message carries the same (lifecycle 4.1, 6.2).
- USD rate in force [C, owner 2026-10-31, replaces "a manual rate stays until changed"]: the channel's post for today (public Telegram channel `wasuntechnology`, read from its web preview; `Bugungi kurs` and `Sana` must both be in the exact form and the day must be today in Tashkent), else a rate a staff member (manager or admin) entered, for 24 hours from the entry, else the Central Bank rate + 40 so'm. The channel outranks a manual rate; a manual rate saved over a channel rate is stored and applies only when the channel has no post for the day. - Customer stock figure and cap [C, 2026-11-09; replaces "customers see no stock" and the [T] visibility setting]: the customer price list and every cart line carry `orderableStock`, the FREE quantity in whole pieces (the staff "Mavjud": each live delivery line's sheet quantity minus the holds of approved orders of ALL organizations), shown as "45 dona bor". The quantity cannot exceed it: the server refuses a cart change and a submit with 409 `STOCK_LIMIT_EXCEEDED` (`details.lines` = product + current figure), and a line that ended up above it (the stock fell later) is the cart problem `STOCK_EXCEEDED`, which blocks the order until the quantity is lowered. ## Architecture conventions

- One module per domain area under `apps/api/src/modules/<name>/`: `identity`, `organizations`, `catalog`, `pricing`, `orders`, `notifications`, `telegram`, `sheets-sync`, `audit`.
- Layers inside a module: controller (HTTP, auth guard, input validation) → service (business rules) → data access (Prisma). No business rules in controllers or in the frontend.
- A module uses another module only through its exported service. Never import another module's data-access code or tables directly.
- Role checks happen in guards/services on the server for every endpoint. Hiding a button is not security.
- Never return a Prisma entity from an endpoint. Map to an explicit response DTO with allow-listed fields (this is what keeps cost data out of customer responses).
- Side effects (Telegram messages, Sheet sync, price posts) go through the outbox / job queue, never inline inside a request handler.
- Business time logic goes through one clock/calendar helper (Asia/Tashkent) so it can be tested with a fake time.

## Code style

- TypeScript `strict` on. No `any` (use `unknown` + narrowing). Explicit types on exported functions and public contracts.
- Types and constants shared by api and web live in `packages/shared`. Do not duplicate them.
- Frontend code used by more than one web app (UI kit primitives, design tokens and base styles, the i18n factory with the `common`/`state`/`apiErrors` catalogs, http client, formatting, Telegram launch and Login Widget) lives in `packages/web-core`, imported as `@core/...` (source, no build step). It never imports app code (`@/...`; ESLint enforces it). Code only one app uses stays in that app.
- Validate input at the boundary with zod only (ADR-001 §3.9; do not mix in a second validation library).
- Naming: files `kebab-case.ts`; classes/types `PascalCase`; variables/functions `camelCase`; enum values `UPPER_SNAKE_CASE`; DB tables/columns `snake_case`; JSON fields `camelCase`.
- Errors: typed domain errors thrown in services, mapped to HTTP status in ONE place. Never swallow errors; never expose stack traces or internals to clients.
- Comments explain WHY, not what. Remove dead code and unused imports.
- Small functions with one responsibility. Prefer simple code over clever abstractions; no abstraction until there are two real uses.
- No new dependency without a stated reason and approval.

## Commands

Run from the repo root unless noted. Node 24 (`.nvmrc`), pnpm 11, Docker Desktop for the local database.

- Setup: copy `.env.example` to `.env` (git-ignored) and set the password, then `docker compose up -d` (PostgreSQL 18 on host port 5433, databases `iorder_dev` and `iorder_test`), then `pnpm install`.
- Quality gate: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`. `pnpm format` / `pnpm format:check` (docs are excluded).
- Task runner: Turborepo (`turbo.json`, pinned 2.11.10). `typecheck`, `test`, `build`, `test:integration`, `check:bundle` and `dev` run through it, so `packages/shared` is built once before the apps that depend on it. Results are cached in `.turbo/` (git-ignored); `test:integration`, `check:bundle` and `dev` are never cached. Package scripts no longer build `shared` themselves: run a single package through Turborepo, e.g. `pnpm turbo run test --filter=@iorder/api`. `pnpm dev` clears `NODE_OPTIONS`, so the VS Code auto-attach debugger does not attach.
- Integration tests (real PostgreSQL, `iorder_test`, migrations applied automatically): `pnpm test:integration`.
- API dev server: `pnpm turbo run dev --filter=@iorder/api`. Production-style run: build, then `pnpm --filter @iorder/api start`.
- Background jobs (pg-boss, ADR-001 §3.4), all OFF by default: the separate worker process `pnpm --filter @iorder/api worker` schedules and runs jobs only with `JOBS_ENABLED=true` plus each job's own switch (see `.env.example`). First create the pg-boss schema and queues once with the owner connection: `pnpm --filter @iorder/api jobs:migrate`. Schedules and windows are [P], in one file: `modules/jobs/job-definitions.ts`. The worker role's privileges: `apps/api/db/pgboss-grants.sql`.
- First real Google Sheet sync (OWNER ONLY, reads the real sheet read-only and writes to the configured database; agents never run it): `pnpm --filter @iorder/api sheets:sync-once -- --confirm-real-sheet`. It prints counts only.
- Web dev servers: staff `pnpm turbo run dev --filter=@iorder/staff` (port 5173), customer `pnpm turbo run dev --filter=@iorder/customer` (port 5174; open `/#tgWebAppData=fake-owner` for a demo customer). Both use the in-memory fake API with demo users; fakes exist only in dev/test or when a build sets `VITE_USE_FAKE_API=true`. `pnpm check:bundle` builds both and fails if fake data or misplaced staff vocabulary ended up in a `dist` (rules in `packages/web-core/scripts/bundle-check.mjs`); CI runs it.
- Migrations (`apps/api/prisma/`): edit `prisma/schema/*.prisma`, then `pnpm --filter @iorder/api db:migrate`. The generated client (`src/generated/`) is git-ignored; `db:generate` rebuilds it and is run by the api scripts.
- Dependency pins: `prisma` and `@prisma/client` are pinned to 7.10.1 (the npm `latest` tag of `prisma` points to a release candidate). TypeScript stays on 6.0.x until typescript-eslint supports 7. pnpm blocks dependency install scripts; the allowed ones are listed in `pnpm-workspace.yaml` (`allowBuilds`).
